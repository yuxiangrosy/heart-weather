## 3. 产品愿景与硬性原则

一句话：每一种真实的心情都值得记录，并让一片属于自己的像素小岛逐渐成长。

1. 视觉为粉蓝、奶油色系**治愈像素游戏风**，有趣但不幼稚。
2. **低压力**：不强制打卡、无断更惩罚、无强迫积极、无负面情绪惩罚；不做情绪诊断或未经记录支持的原因猜测。
3. 心情记录：16 种天气（默认快速显示 8 种、其余展开）；每条可选最多 3 个细分标签，可留文字；一天可记录多次，支持编辑/删除。
4. 日历、周/月统计需**区分记录条数和记录天数**。
5. **天气岛从极简、留白较多的荒地开始**，只有少数草和石块；植物与风景由真实心情逐步创造，所有天气都有正向的自然变化。
6. 一天可记录多条心情，但**最多形成一处长期岛屿景观**；天气氛围可随最新记录改变。植物可点击看回忆，支持时光回放。
7. 岛屿不会因用户暂停记录而衰败、死亡或被惩罚。
8. 规划未来的**心之群岛**：不同主题岛可自由切换或设为家，旧岛/回忆/成长保留；用户身份、历史日记、宠物与收藏属于全局，不随搬家清零。
9. 规划**宠物陪伴**：猫咪或狗子，宠物跟随旅行，不因断更饿死/离开。后续可扩展互动、配饰、小窝。
10. 规划**鼓励陪伴角色**（温暖/积极/清醒/幽默）及**虚拟出气屋**（虚构漫画怪物、非真实人物可识别肖像），不把发泄强制引导为积极心情。
11. 可选好友来访需明确授权与隐私界限；当前无账号无云端日记共享。

## 4. 当前真实工程架构（不要误认为已迁移 React）

当前可运行版本是**零外部依赖 HTML + CSS + JavaScript** 的静态 PWA：
- index.html：HTML 入口及 iPhone 图标配置
- app.js：记录/统计/Canvas 像素天气岛/备份/恢复逻辑
- styles.css：视觉样式
- sw.js：PWA 离线资源缓存
- manifest.webmanifest：PWA 标识与入口
- icons/：现有满意的粉蓝像素图标
- tests/：现有模拟数据库与浏览器相关测试
- README.md、CHANGELOG.md：仓库维护说明

未来可以重构模块或采用 React、Dexie 等，但**任何重构首先确保数据兼容和实测安全**，不能为了换技术栈牺牲现有用户记录。

### 必须保持的持久化契约

- GitHub Pages URL、应用范围、manifest 的 id/start_url/scope = "./" 不随意改变。
- IndexedDB 名称 = heart-weather-db、版本 = 1；已有对象仓库 moods、growth、meta、drafts。
- 现有备份 JSON 识别 format = mood-weather-backup、schemaVersion = 1。
- 当前备份包含心情、小岛与设置，SHA-256 校验；导出后需用户自行存到 iCloud Drive 并确认。它**不是自动云备份**。
- 当前导入恢复会**覆盖**现有数据，不是合并。破坏性测试只能用隔离的测试数据库/测试站点及合成日记。
- 从 v0.1.x 升级到 v0.2.0 已在真实 iPhone 验证记录保留，但未来升级仍须回归。
- **绝不要求用户删除现有主屏幕 App、重新添加图标、清理 Safari 数据来“刷新”**。不同 PWA 安装实例可能拥有独立本地数据。
- 不得把真实日记、iCloud 备份、密钥、API Key 提交到公开 GitHub 仓库。

- 后续 v0.4+：猫咪与狗子；再扩展多岛、人物陪伴、虚拟出气屋。具体版本时间不作承诺。

### v0.3.0 特别说明

当前 review() **已经具有周/月统计与本地模板文字**，但不是 AI、没有定期生成历史报告的完整机制。
目标是周结束/月结束后在**下次打开 App**时发现并生成信件、可回顾旧信件；不假装 PWA 关闭时仍能后台准时运行；保证“事实有据、稀疏数据不乱推断、可备份”。

## 6. Work 模式下一步任务建议

1. 连接 GitHub 仓库、阅读 README.md / CHANGELOG.md / app.js / tests/ / Issue #2/#3；校验 main 的真实状态。
2. 先处理 Issue #2 的安全验收和必要的小型修复；避免在 iPhone 的生产数据上尝试覆盖恢复。
3. 需要更改代码时新建功能分支，运行测试，提交 PR，报告测试覆盖/未覆盖；合并前确保已有备份、与原 PWA 身份兼容。
4. 完成 #2 后实现 Issue #3；交付实际可用的页面和逻辑，不只给概念或设计稿。
5. 每轮迭代后给用户极短的产品验收清单，重点检查手机体验和旧数据连续性。

## 7. 交接完成的判断标准

- Work 已读取本文件及 GitHub main，而非仅凭口头描述继续。
- 能清楚区分：已经发布的代码、已在 iPhone 实测的功能、计划中的功能和风险。
- 第一项落地工作从 Issue #2/#3 继续，且不覆盖日记或反复要求用户手动上传 ZIP。
- 主仓库的正式版本、PR、Issue、备份兼容契约成为后续团队式工作的唯一工程基线。

> Work 模式不能直接“继承”原 Chat 聊天的全部消息；这份交接文件专为新 Work 任务提供连续上下文。如有细节争议，以代码、Issue 与用户最新确认意见为准。
